## F2 — `import_step` cannot read the file `export_step` just wrote (2026-08-07)

- symptom: `{"op":"export_step","in":X,"file":"cad/frame.step"}` with `--out-dir .` writes
  `./cad/frame.step` (report `file` confirms), but the round-trip gate
  `{"op":"import_step","file":"cad/frame.step"}` in the same program fails
  `io: op 'g_rt': cannot read 'programs/cad/frame.step': No such file or directory`.
  Export paths join `--out-dir`; import paths join the PROGRAM FILE's directory. Reaching the
  written file with `"../cad/frame.step"` is then refused:
  `invalid_param: path '../cad/frame.step' must not contain '..' (it would escape the sandbox)`.
- minimal repro: a two-op program in `programs/` that exports to `cad/x.step` with
  `--out-dir <part dir>` and immediately imports `cad/x.step`.
- expected vs actual: SPEC §2.12 asks every campaign to assert the STEP round-trip in-program,
  and the documented layout puts programs in `programs/` and STEP in `cad/`. With those two
  path rules and the `..` ban, the round-trip gate is unwritable for the documented layout.
- workaround used: the part programs export the STEP twice — the shipped
  `cad/<name>.step` and a transient `programs/_rt_<name>.step` that `import_step` can reach
  as `"_rt_<name>.step"`. Documented in README "Reproducing"; the transient is regenerated by
  the same program. Costs a duplicate 2.5 MB / 12.5 MB file per part.

## F3 — cookbook says ace_fea body-load magnitude is N.m-3; the code reads it as N/kg (2026-08-07)
- symptom: `{"kind":"body","magnitude": 24328.8, "direction":[0,0,-1]}` (= 2 g x PLA density
  1240 kg/m3, i.e. N.m-3 per the digest) on a 9.27e-6 m3 platform produced
  `max_von_mises_pa = 92941359.7` (92.9 MPa) and `max_displacement_m = 1.4847e-3` — a 2 g
  handling shake reading as gross yielding. Expected ~0.23 N of total inertial load.
- minimal repro: any ace_fea job with a body load; compare the receipt's implied total force
  against `magnitude x volume`. Source of truth:
  `~/Work/ACE/engine/verify/fea.py:1035 _apply_body_load` docstring —
  "per-node force = magnitude(N/kg) * direction * tributary mass".
- expected vs actual: `campaign/digests/tools_cookbook.md:76` documents `loads` as
  "(units N / N.m-3 / Pa)" for point/body/pressure, i.e. body = force per unit VOLUME.
  The binary multiplies `magnitude` by tributary MASS, so magnitude is an ACCELERATION in
  N/kg (m/s2). Passing the documented N.m-3 value over-loads by a factor of the density
  (1240x here). Nothing warns: exit 0, `ok:true`, and the number is silently 1240x wrong.
  `engine/verify/fea_tet.py:328` states the same N/kg convention in a comment, so the code
  is self-consistent and the digest is the drifted artefact.
- workaround used: pass 2 g as `magnitude = 19.62` (N/kg). Verified by the receipt's
  displacement dropping to the elastic range. The campaign's FEA generator carries the
  correction and the citation inline (programs/gen_fea.py).

## F4 — tolerance_stack.py double-counts an ASYMMETRIC tolerance in the WORST-CASE band (2026-08-08)
- symptom: a chain of A = 10.0 with `{"plus":0.0,"minus":0.10}` (dir +1) minus B = 9.0 with
  `"tol":0.0` (dir -1) returns `nominal_gap 0.95, worst_min 0.85, worst_max 0.95`.
  The true band is nominal 1.00, worst_min 0.90, worst_max 1.00.
- minimal repro:
  `{"chain":[{"name":"A","nominal":10.0,"tol":{"plus":0.0,"minus":0.10},"dir":1},
             {"name":"B","nominal":9.0,"tol":0.0,"dir":-1}],
    "closes":{"min_required":0.0,"max_allowed":5.0}}`
  `python3 tools/tolerance_stack.py probe.json`
- expected vs actual: the docstring (tolerance_stack.py:18-20) says the asymmetric->bilateral
  mid-shift is used **for RSS**. In the code the mid-shift is applied to the SHARED
  `nominal_gap` (line 85) while the WORST-CASE accumulators keep the full one-sided `plus`
  and `minus` (lines 81-82), so `worst_min = nominal_gap - worst_lo` subtracts the full
  minus from an already-shifted nominal. The error is (plus - minus)/2 per asymmetric
  element: **pessimistic on worst_min, OPTIMISTIC on worst_max** — the max side is the
  dangerous one, since a `max_allowed` check can pass on a band that is really wider.
- workaround used: this campaign states every tolerance BILATERALLY (an optic of
  25.40 +0/-0.10 is entered as nominal 25.30 +/- 0.10, which spans the same interval), so no
  asymmetric `{plus,minus}` reaches the tool. Verified: the I1b retention chain then returns
  the hand-checked worst_min. Entries are in programs/gen_tol.py with this note inline.

## F11 — `physlib.run_tool`'s `timeout=` raises `TimeoutExpired`, so a timed-out analysis leaves NO receipt (2026-08-08, repair pass)
- symptom: `physlib.run_tool` calls `subprocess.run(..., timeout=timeout)`. On timeout Python raises
  `subprocess.TimeoutExpired`, which propagates out of the calling generator: the program dies with a
  traceback and `L.save()` is never reached, so the failed row leaves no receipt at all — it VANISHES
  rather than failing. That is the one outcome DELIVERABLE_SPEC §3 forbids ("Silence is the one
  forbidden outcome").
- minimal repro: `python3 programs/gen_tet.py --elem 1.5 --timeout 8` against the pre-fix gen_tet.py.
- expected vs actual: a resource kill is a recorded negative result; the pipeline treated it as an
  unhandled exception.
- workaround used: `gen_tet.py` now wraps the call, catches `TimeoutExpired` and synthesizes the honest
  `ok:false` receipt with `_campaign.wall_budget_s` and `_campaign.killed_at_wall_budget`. The same
  guard belongs in `physlib.run_tool` itself for every caller, but the fix is campaign-local by design
  (§4: tools/ is untouchable, and physlib is shared by nine generators — changing its contract mid-repair
  would have been the larger risk).
